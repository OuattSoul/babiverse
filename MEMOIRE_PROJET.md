## 1. Le jeu en bref

- Simulateur de vie et d'entrepreneuriat dans un quartier fictif d'Abidjan (**Cité Akwaba**), jouable dans le **navigateur mobile** (PWA).
- Le joueur : crée son **compte** (nom d'utilisateur sans espace + mot de passe pour se connecter, e-mail facultatif de récupération), puis son personnage (le nom d'utilisateur sert de nom dans le jeu ; genre, apparence, profil), explore la rue, entre dans les bâtiments, mange, fait la sieste, livre des colis pour M. Diabaté, ouvre un **kiosque à boissons**, achète une **parcelle**, y construit, loue un **panneau publicitaire**.
- Principe de design : **tout se passe dans le monde**, les panneaux DOM sont secondaires.
- Monnaie **strictement virtuelle** (franc CFA virtuel, entier ≥ 0). Jamais de paiement réel, conversion ni blockchain.
- Solo (stocks des commerces propres à chaque joueur), mais **monde partagé** : parcelles, constructions, publicités et maisons des autres joueurs sont visibles (rafraîchies au battement de cœur, 45 s). **Rencontres** (ADR 0010) : les autres joueurs présents dans la même zone partagée apparaissent en temps quasi réel (boucle sociale de 2 s) ; on peut leur proposer de discuter, les appeler (voix WebRTC) ou devenir amis.

## 2 bis. Atelier d'assets (Babiverse Asset Studio)

- Emplacement : `babiverse-asset-studio-admin/babiverse-studio/` (README, `docs/GUIDE_ADMINISTRATEUR.md`, `docs/FAMILLES.md`, `docs/INTEGRATION.md`, `docs/DEPLOIEMENT.md`, `docs/AUDIT.md`). Environnement Python propre : `backend/.venv`.
- Séparation famille technique (code : `taxonomy.FAMILIES`) / catégorie métier (table `categories`, administrable) / définition versionnée (`asset_versions`, dépendances figées dans `pins` à la publication) / instance (`instances` : `asset_id@version` + scène).
- Familles : bâtiment (façade modulaire), intérieur, route, surface, objet (mobilier urbain, végétation), meuble, véhicule, personnage (calques SVG), composant de personnage (SVG assaini, canaux `var(--babi-<canal>, défaut)`), **composant modulaire** (`component`). Capacités réelles déclarées par famille et affichées.
- **Ateliers modulaires** (`#/modulaire`, depuis le 2026-10-12) : même principe que les personnages pour bâtiment, véhicule, objet, meuble et surface — représentation `modular`, `properties.modular = {kit, base, base_colors, base_pattern, colors, layers}`. 6 kits dans `taxonomy.KITS` (façades 0 0 200 280, véhicules 0 0 240 140, végétation, mobilier urbain et étals, meubles, surfaces vues de dessus) : une base déclare des points d'ancrage en **listes de positions** (la pièce se répète : fenêtres par étage, roues par essieu, coussins par place) ; pièce sans point sur la base = incompatible. Règles serveur `validation.check_assembly` et miroir client `frontend/src/modular/compose.ts` (`composeKit`, `checkAssembly`, `randomAssembly`, `countCombinations`, `libraryChecks`). Bibliothèque de départ `backend/app/seed_kits.py` (243 SVG, réglage `seed.kits`) ; page de kit : éléments, rue de test 96/40 px, combinaisons, tests de bibliothèque (dont mesures réelles dans le navigateur) ; studio par onglets, variantes, JSON ; import/édition de composants. Rendu carte : image debout (sols projetés sur l'emprise). Routes `GET /api/kits/parts`, `GET /api/assets/{id}/render` (personnage ou assemblage) ; catalogue d'exécution : `kits`, `kit_parts`.
- **Personnages hommes / femmes** : le corps déclare `gender` (male/female), un composant `genders` (réservé à). Règle serveur `character.gender` (`validation.check_outfit`), miroir client `fitsGender` / `checkOutfit` (`character/compose.ts`) ; l'atelier masque les composants de l'autre genre et les retire au changement de silhouette ; le générateur les respecte. Emplacement `makeup` (Maquillage). Bibliothèque : 71 composants (23 réservés aux femmes, 4 aux hommes), 6 habitants (Kouadio, Yao, Konan ; Awa, Aminata, Tantie Adjoua). Base existante mise à niveau par le réglage `seed.characters_v2` (`seed.upgrade_character_parts`, nouvelles versions publiées seulement si la définition diffère, brouillons en cours non touchés).
- **Fichiers de la médiathèque** : sur disque (`BABIVERSE_MEDIA_STORAGE=disk`, défaut) ou en base (`database`, table `media_blobs` sha256 → BLOB/BYTEA, migration 3) pour Render gratuit dont le disque s'efface ; accès par `service.store_file` / `service.read_file` (aussi export/import de lots) ; `python -m app.media_to_db [base] [dossier]` verse des fichiers existants dans la base. Les lots d'import restent sur disque entre aperçu et application.
- **Base** : PostgreSQL si `BABIVERSE_DATABASE_URL` (ou `BABIVERSE_DB`) est une URL `postgres://` ; sinon fichier SQLite. Un seul dialecte dans le code (paramètres `?`, `ON CONFLICT DO NOTHING`) : `db.PgConnection` (psycopg 3) traduit `?`→`%s`, rend des lignes `db.Row` lisibles comme `sqlite3.Row`, écrit les booléens en 0/1, adapte le DDL (`REAL`→`DOUBLE PRECISION`, identité au lieu d'`AUTOINCREMENT`) ; version de schéma dans la table `schema_version` (PostgreSQL) ou `PRAGMA user_version`. Base de dev créée avec `LOCALE 'C'` (ordre de tri de SQLite). `backend/.env` lu au lancement réel seulement (`config.load_env_file`, jamais en tests). Reprise d'une base SQLite : `python -m app.copy_to_postgres [chemin.db] [URL]` (cible vide, effectifs vérifiés). `GET /api/system` : `db_engine`, `db_path` sans mot de passe. Attention : PostgreSQL exige toutes les colonnes non agrégées dans le `GROUP BY`.
- Connexion partagée unique : une requête à la fois (`main._gate` dans la dépendance `db`, qui termine chaque requête par un commit, ou un rollback si elle échoue, et relève une transaction PostgreSQL en erreur) — des lectures simultanées produisaient des 404/500 aléatoires sous SQLite.
- Cycle `draft → in_review → validated → published → superseded`, archivage, retour à une version (nouveau brouillon), comparaison, migration explicite des instances.
- Médias sur disque par empreinte (`media/`), type vérifié par signature, liens signés ; migrations numérotées ; config par variables `BABIVERSE_*` ; en production : secrets obligatoires, aucun compte de développement.
- Intégration avec le jeu : **pack de jeu** `GET /api/runtime/game-pack` (`app/gamepack.py` ; en-tête `X-Babiverse-Game-Key` = `BABIVERSE_GAME_KEY`, défaut `babiverse-dev` hors production, ou session `asset.export`) : garde-robe (`gamepack.WARDROBE_SLOTS` : silhouettes avec `gender` — déclaré, sinon déduit du nom —, coiffures, hauts, bas, robes, vestes, chaussures, couvre-chefs, accessoires de cheveux, lunettes, bijoux, montres, sacs, barbes, maquillage ; chaque composant porte `bodies` et `genders` ; visage par défaut par silhouette respectant son genre ; teintes), habitants publiés (SVG figé, PNJ attribué, `roams`), intérieur de la maison, composants SVG (`id@version`), `revision`. Page **`#/jeu` « Intégration au jeu »** (`views/game.ts`) : intérieur de « Chez moi », habitant de chaque PNJ (auto = habitants publiés les plus récemment ajoutés d'abord, même silhouette si possible, ou « garder l'apparence du jeu »), promeneurs oui/non, publication en lot des habitants brouillons (`POST /api/game/publish-inhabitants`), téléchargement du pack ; réglages en table `settings`, clés `game.*` (`GET/PUT /api/game/settings`, écriture `asset.publish`). Restent pour les autres familles : `GET /api/runtime/catalog` et `GET /api/runtime/game-adapter`.
- **Comportements à prérequis** (`frontend/src/behaviors.ts`, miroir de `validation._validate_behaviors`) : à l'ajout, « Zone d'interaction » crée/réutilise une zone `interaction` (`accueil`, case devant l'entrée principale ou au sud de l'objet) et la choisit dans une liste (plus de texte libre) ; « Logement attribuable » coche `assignable_to_player` ; « Vente de marchandises » sur un bâtiment crée la façade commerciale ; « Ouvrir un intérieur » est refusé tant qu'aucun intérieur n'est associé. L'éditeur montre la section Zones aussi pour les objets. L'assistant pose une entrée d'urgence (santé) ou de service (sécurité) pour les catégories `service_entrance_recommended`.
- **Carte du jeu** (`#/jeu/carte`, `views/gameMap.ts` + dessin `views/gameMapRender.ts`, depuis le 2026-10-12, ADR 0009) — affichage : couche de base mise en cache (sol par type de case, routes avec marquage et passages piétons, trottoirs, place, parcelles en pointillé, lotissement hachuré, bâtiments vus de dessus avec ombre, toit, bande de façade du côté de l'entrée et porte, arbres/palmiers/buissons, mobilier en pictogrammes, éléments de l'atelier à leurs couleurs avec liseré bleu, éléments retirés en fantôme barré, règles graduées en cases, quadrillage tous les 10, étiquettes posées sans chevauchement — éléments placés, enseignes, parcelles, rues, lotissement) + couche interactive (survol, sélection, zone tracée avec cases libres en vert et occupées en rouge, taille affichée) ; infobulle (nom, type, case, état : libre / raison du refus / protégé / retiré) ; barre d'outils : zoom − / +, « Centre-ville » (vue de départ), « Toute la carte », calques Étiquettes, Quadrillage, Zones libres (mémorisés dans le navigateur) ; molette = zoom centré sur le curseur, clic droit / clic molette / Espace + glisser = déplacer la vue ; légende ; le calque expose `data-scale` / `data-ruler` pour les tests de bout en bout. Fonctionnement : la vraie ville du jeu, générée par les modules du client importés sous l'alias Vite `@jeu` (`client/src` ; déclarations `src/jeu.d.ts`) — **reconstruire l'atelier quand la ville du jeu change**. L'administrateur trace une zone (cliquer-glisser), choisit l'orientation et un élément publié qui y tient (bâtiment, objet, véhicule, surface ; vignette, raison du refus sinon) ; règles `client/src/world/placement.js` (mêmes que le jeu). Clic sur un élément placé : détail, état dans le jeu, retrait. **Éléments d'origine** (bâtiments, arbres, mobilier de la ville du jeu) : clic → « Retirer de la carte » / « Remettre sur la carte » (croix rouge sur la carte, liste « Éléments d'origine retirés ») ; protégés (raison affichée) : commerces avec intérieur ou PNJ (épicerie), emploi (dépôt Diabaté), destinations de livraison (maquis, Kouassi, Mme Bamba), kiosque du joueur, étal de garba, parcelles, panneaux publicitaires ; un élément retiré libère sa place pour un placement. Réglage `game.removals`, `POST /api/game/removals {key, label}`, `DELETE /api/game/removals/{key}` (écriture `asset.publish`) ; pack : `removals` (clés). Serveur : `app/gameworld.py` (réglage `game.placements`, `GET/POST/DELETE /api/game/placements`, écriture `asset.publish` ; vérifie famille, publication, dimensions selon l'orientation, chevauchements — une surface peut passer sous un autre élément) ; le pack de jeu y ajoute `placements` (données de rendu, intérieur associé du bâtiment) et `kits` (objets modulaires).
- **Villes et cartes** (`#/monde`, `views/world.ts`, service `app/worldmaps.py`, migration 4, ADR 0012) : villes → zones → cartes jouables (identifiant = zone du jeu, ≤ 32 caractères, ni `quartier`/`maison`/`epicerie` ni `int_`). Éditeur de carte (`#/monde/carte/<id>`) : aperçu vu de dessus (emprises, zones, arrivée ; glisser pour tracer la zone de l'objet sélectionné), paysages 3D (import GLB / glTF dans la médiathèque, catégorie `landscape` ; instance x, z en cases, rotation par quarts de tour horaires, échelle, infranchissable ; révision du fichier **figée** à l'enregistrement ; emprise calculée par le serveur, `worldmaps.footprint`), objets interactifs (`shop` / `info` / `door`, actif ou non, zone tracée ou déduite d'un objet nommé unique du modèle, libellé, texte, destination), point d'arrivée, accès depuis la Cité Akwaba (case, texte du panneau). Brouillon (`PUT /api/game/maps/{id}/draft`) sans effet sur le jeu ; publication (`POST …/publish`, permission `world.publish`) refusée tant qu'il reste un problème (fichier absent ou archivé, emprise hors carte, arrivée dans un obstacle, destination inconnue, pas de sortie, pas d'accès, case d'accès déjà prise) ; versions immuables `map_versions` ; désactiver / réactiver. Routes : `GET /api/game/world`, `POST /api/game/world/cities|districts`, `POST /api/game/maps`, `GET /api/game/maps/{id}`, `…/disable|enable` (le préfixe `/api/world` reste aux scènes de test) ; `GET /api/runtime/models/{média}/{révision}` (clé du jeu, seulement les modèles d'une carte publiée). Pack de jeu : `maps` (versions publiées : dimensions, sol, arrivée, paysages + `models` {média, révision, mime, sha256, bbox}, objets, accès). Médiathèque : `app/gltf.py` (glTF 2.0, GLB ou glTF autonome en `data:`, sans Draco/Meshopt, dimensions, objets nommés et doublons, triangles), kind `model`, `BABIVERSE_MAX_MODEL_MB` (20 ; une image reste plafonnée à `BABIVERSE_MAX_UPLOAD_MB`, 413 au-delà). Permissions `world.manage` (éditeur, publieur), `world.publish` (publieur).

## 3. Architecture générale

```
Client (navigateur)                                  Serveur Django
 main.js ── boot : config → connexion/inscription      views.run_action :
   │        → état → création si pas de perso                auth → verrou Character (select_for_update)
 engine3d/World3D  (rendu, caméra, joueur, PNJ)            → idempotence → tick(temps)
 world/*  (logique PURE, testée : grille, ville,            → apply_position → handler dans un SAVEPOINT
           sélection, interactions, chemins…)              → missions.emit("balance") → version+1
 game/actions.js ── net/api.js ──── HTTPS JSON ──────►     → réponse {ok, result|error, state}
 state/store.js (dernier état serveur + bus d'événements)  services/* (core, life, work, business,
 ui/* (HUD, fiches, panneaux, menu du bas, écrans)                   missions, plots, homes, state)
                                                         rules.py = TOUTES les valeurs d'équilibrage
```

Règles d'or :
1. **Le serveur fait autorité.** Le client n'envoie que l'intention + `pos: {zone, x, y}`. Aucune valeur économique calculée localement ; le client remplace son état par `state` à chaque réponse.
2. **Modules purs séparés du rendu** : `client/src/world/*` ne dépend pas de Three.js → testés avec Vitest. Le monde ne connaît pas l'économie : il passe par le registre `world/interactionTypes.js` qui lit l'état et appelle `game/actions.js`.
3. **Données d'abord** : ajouter un bâtiment, une parcelle, un panneau ou un objet interactif = ajouter une ligne de données.
4. Les services backend ne connaissent ni rendu ni UI : `(char, data, now) → résultat` ou `GameError(code, message, status)`.

Détails : [docs/architecture.md](docs/architecture.md).

### 4.2 API (`/api/…`)

| Route | Idempotence | Effet |
|---|---|---|
| `POST auth/register` | — | `{username, password, email?}` → compte + `token` (+ lien de confirmation si e-mail) ; avec le jeton d'un ancien invité : rattache les identifiants, garde la partie (pas de nouveau jeton) |
| `POST auth/login` | — | `{username, password}` → nouvelle session `token` (l'e-mail n'est pas un identifiant) |
| `POST auth/email` | — | `{email, password}` : ajoute/change l'adresse (en attente jusqu'à confirmation ; l'ancienne est prévenue) ; `email` vide = retirer |
| `POST auth/email/resend` | — | renvoie le lien de confirmation (3 envois/h) |
| `POST auth/email/verify` | — | `{token}` (sans session) : confirme l'adresse du lien `#verify=` |
| `POST auth/logout` | — | ferme cette session, ou toutes avec `{everywhere: true}` |
| `POST auth/password/change` | — | `{current_password, new_password}` ; ferme les autres sessions, alerte e-mail |
| `POST auth/password/forgot` | — | `{login}` (nom d'utilisateur ou e-mail) ; réponse toujours identique ; envoie `PUBLIC_URL/#reset=<jeton>` à l'adresse **confirmée** seulement |
| `POST auth/password/reset` | — | `{token, password}` ; ferme toutes les sessions, lève le verrou, renvoie un nouveau `token` |
| `GET account` | — | `{registered, username, email (confirmée), pending_email}` |
| `GET config` | — | règles publiques |
| `GET atelier/pack` | — | ouvert sans session : `{pack}` (pack de l'atelier ou null), `ETag` = révision (304 si inchangé) |
| `GET atelier/models/<média>/<révision>` | — | ouvert sans session, sans limitation : fichier GLB / glTF d'une carte publiée par l'atelier (annoncé par le pack, empreinte vérifiée), `Cache-Control: immutable` ; 404 sinon |
| `GET state` | — | tick + état complet (ou `null` si pas de perso) |
| `POST character/appearance` | oui | changer d'apparence après la création (gratuit) : même validation que la création (`state.clean_appearance`) ; tenue de l'atelier devenue indisponible → 400 `invalid_appearance`, apparence inchangée |
| `POST/DELETE character` | — | créer (nom facultatif : sans nom, **le nom d'utilisateur du compte** ; un invité sans identifiants doit en donner un ; profil, apparence ; `appearance.studio = {body, skin, hair_color, layers}` si la garde-robe de l'atelier est utilisée, validée par `atelier.clean_look`) / supprimer le perso (« Recommencer » : libère parcelle et pub ; **la maison du lotissement est conservée**, liée au `Player`) |

| `POST sync` | non | battement de cœur : position + tick |
| `GET ledger` | — | 30 derniers mouvements |
| `GET presence` | — | ouvert sans session : `{players_online, visitors: null}` = joueurs dont `last_seen_at` date de moins de 2 min (`PRESENCE_WINDOW`) ; l'appel d'un joueur connecté rafraîchit son `last_seen_at`. Pas de mode visiteur → `visitors` toujours null |

| `POST npc/talk` | non | événement `talk_npc` pour les missions |
| `POST jobs/start`, `jobs/complete`, `jobs/abandon` | oui | emploi |
| `POST jobs/deliver` | non | livrer un colis |
| `POST business/open`, `business/restock`, `business/sell` | oui | kiosque |
| `POST missions/accept` (non) · `missions/claim` (oui) | | missions |
| `POST plots/buy`, `plots/build`, `ads/rent` | oui | monde partagé |

### 4.3 Modèles

- `Player` (username unique en minuscules, `email` = adresse **confirmée** unique, `email_verified_at`, `pending_email`, password haché, failed_logins, locked_until, password_changed_at, last_seen_at ; propriété `registered`) 1—n `AuthToken` (token_hash unique, last_used_at), 1—n `PasswordReset` et 1—n `EmailVerification` (token_hash, [email,] expires_at, used_at), 1—1 `Character` (nom, profil, apparence, `balance` ≥ 0 par contrainte, hunger, energy, needs_updated_at, last_rest_at, zone, pos_x/pos_y en **pixels de grille**, `version`).
- `Character.appearance` : `{skin, outfit, hair}` (modèle 3D d'origine) et, si créé avec la garde-robe de l'atelier, `studio: {body, skin, hair_color, layers: {slot: {part: asset_id, colors}}}` (identifiants d'assets : le rendu suit la version publiée courante).
- `InventoryItem`, `ShopStock` (par joueur, par jour), `LedgerEntry` (journal immuable : start, purchase, job_wage, mission_reward, business_open, business_sale, business_passive, plot_buy, plot_build, ad_rental), `IdempotencyRecord` (unique par perso+clé), `MissionState` (available → active → completed → rewarded), `JobShift`, `Business` (1 par perso : stock, prix, passive_carry, units_sold, revenue, spent).
- `PlotClaim` (`plot_id` **unique** → arbitre la concurrence ; template/x0/y0/facing/name du bâtiment), `AdCampaign` (`slot` unique), `Home` (1 par `Player`, `slot` unique, `(x,y)` unique, template, facing).
- **Rencontres** : `SocialRequest` (sender, recipient → Character, kind chat/call/friend, status pending/accepted/declined/missed/cancelled, created_at, answered_at, `read_at` = vue par le destinataire, `outcome_read_at` = réponse vue par l'expéditeur, `ended_at` = fin d'un appel décroché), `CallSignal` (call, sender, kind, payload JSON), `Friendship` (low < high, unique), `ChatMessage` (sender, recipient, text ≤ 500, read_at). `Character.seen_in_world_at` = dernière interrogation sociale.
- `BugReport` (player → CASCADE, message, zone, user_agent, created_at), visible dans `/admin/` (comme `Player`, sans l'empreinte du mot de passe).

### 4.4 Zones connues du serveur

`ZONES` = cartes **publiées** du catalogue `shared/maps.json` (aujourd'hui `("quartier", "maison", "epicerie")`) + tout identifiant `int_<id>` (intérieurs générés, motif du catalogue `^int_[A-Za-z0-9_]{1,40}$`). Zone de départ : `start_map` du catalogue (`maison`). Une carte passée `disabled` n'est plus reconnue : la position enregistrée d'un joueur qui s'y trouvait reste en base, les nouvelles sont ignorées. Position validée grossièrement (0 ≤ x,y ≤ 1 000 000 px) ; la géométrie fine est côté client.
**Intérieurs privés** : `int_pb_<parcelle>` n'est accepté que pour le propriétaire de la parcelle, `int_home_<slot>` que pour le propriétaire de la maison (réservé pour l'intérieur à venir) ; sinon la position est ignorée (zone inchangée, avertissement dans le journal `game`). Côté client, `World3D.enterBuilding` n'ouvre pas la porte d'un bâtiment dont `owner` est défini et `mine` faux (la fiche s'ouvre à la place).

## 6. Monde et navigation

- **Unités** : 1 case = 32 px de grille = 1 unité 3D. Positions sauvegardées en pixels. x = est, z (= y grille) = sud.
- **Ville (`quartier`)** : 2 rues E-O (Avenue Akwaba y=12, Rue des Fromagers y=26), 2 boulevards N-S (x=17, x=37), carrefours/passages piétons déduits. **11 bâtiments publics** (tous 2×2 cases désormais, gabarits `TEMPLATES`) : voisins, épicerie, maquis, dépôt Diabaté, Kouassi, couture, pharmacie, transfert, Mme Bamba… **12 parcelles** P01–P12 (P12 indisponible, réservée mairie). **5 supports pub** (4 panneaux + 1 totem ; 3 annonces fictives actives, 2 libres). Mobilier : lampadaires, poteaux + câbles, bancs, poubelles, stops, panneaux directionnels, véhicules. Circulation et passants animés.
- **Taille de la ville non fixe** : `cityExtent` l'agrandit vers l'est/sud selon le contenu (~108×105 cases avec le lotissement). L'origine ne bouge jamais → positions sauvegardées toujours valides.
- **Lotissement Akwaba** (`shared/city.json → residential`) : zone 64×64 en (43, 40), 1 024 emplacements de 2×2, maisonnette façade sud. Chaque nouveau joueur reçoit **le premier emplacement libre** (même transaction que la création du perso). Bloc plein → nouveau bloc de 64×64 au sud (`blocks` envoyé par le serveur → `setResidentialBlocks` régénère la ville). Emplacements libres = bordure + fond blanc + « + » (instancié). Seule « ma maison » a une étiquette de carte (« 🏠 Chez moi »). **Ma maison est « Chez moi »** : `homeBuildings` lui donne `zone: 'maison'` → la toucher ouvre le studio ; en sortant (`from_maison`), `World3D.spawnTile` place le joueur devant sa porte (repli `[6, 12]` si la maison n'est pas encore connue). Les maisons des autres restent fermées.
- **Politique de navigation par zone** (ADR 0005) :
  - ville (`navigation: 'camera'`) : glisser = caméra, clic = **fiche** de l'objet, **jamais** de marche ; déplacement au joystick/clavier ou via « Y aller : … » ;
  - logements/intérieurs (`'walk'`) : clic au sol = marche (A*), clic sur meuble/porte = fiche.
- **Intérieurs** : studio et épicerie dessinés à la main ; tous les autres bâtiments publics et les constructions des joueurs ont un intérieur généré. On entre en touchant le bâtiment (fondu 200 ms, sauvegarde immédiate, reconstruction de la zone).
- **Menu du bas** : « Chez moi » → zone `maison` (le studio de ma maison du lotissement) ; « Ville » → vue d'ensemble dézoomée (2ᵉ appui : retour au personnage) ; « Opportunités » → cartes (missions, livraisons, kiosque, parcelles, pub) avec bouton qui **localise** l'objet dans la ville et ouvre sa fiche ; « Mon profil ».
- **LOD** : détails et noms des PNJ masqués de loin, étiquettes de lieux (pastilles d'icône : 🛒 épicerie, 🍲 maquis, 📦 dépôt, 🧵 couture, 💊 pharmacie, 💸 transfert, 🏪/🏡 constructions, 🏠 chez moi ; le nom reste dans la fiche) affichées de loin, brume repoussée au dézoom.
- **Jour/nuit** : soir 18 h, nuit 19 h 30 – 5 h 30 (heure serveur), lampadaires allumés.
- **Habitants de l'atelier** (si le pack est chargé) : chaque PNJ prend l'apparence de l'habitant attribué dans l'atelier en gardant nom, rôle, dialogues, place et comportement (flâneur/immobile) ; les habitants sans PNJ se promènent sur les trottoirs du centre (≤ 24, nommés, dialogue = salutation de l'atelier) ; passants et clients du kiosque prennent aussi leurs apparences. Rendu en personnages en volume (formes rondes articulées habillées des vues face, dos et profil de l'atelier, éclairées comme la scène), qui marchent comme le modèle 3D. Maison du joueur : intérieur choisi dans l'atelier (même identifiant `maison`). Création du personnage : nom = nom d'utilisateur (pas redemandé) ; **Genre** (Féminin / Masculin) qui filtre aussitôt silhouettes et composants, silhouette (si plusieurs dans le genre), peau, puis coiffure (+ couleur), haut, bas, robe, veste, chaussures, couvre-chef, accessoire de cheveux, lunettes, bijoux, montre, sac, barbe, maquillage — seulement les composants publiés compatibles, chacun en vignette dessinée avec le vrai composant ; « 🎲 Au hasard » reste dans le genre actif ; aperçu SVG. Le même sélecteur (`appearancePicker` dans `ui/screens.js`, garde-robe ou apparence classique) sert à **changer d'apparence** depuis « Mon profil » (`appearancePanel`), en partant de l'apparence actuelle.
- **Rencontres entre joueurs** (ADR 0010) : dans la ville et les intérieurs publics (pas « Chez moi » ni les intérieurs privés), les autres joueurs connectés apparaissent avec leur nom et marchent avec ~2 s de retard. À moins de 3 cases, la barre « 💬 Chatter / 📞 Appeler / 🤝 Ajouter ami » s'affiche (cachée pendant une fenêtre). L'autre joueur reçoit la demande en surimpression : Accepter, Refuser ou ✕ (ou rien pendant 20 s) → elle reste dans 🔔, marquée lue, et peut encore être acceptée. Discussion acceptée → fenêtre de discussion des deux côtés ; ami accepté → « ★ Ami » (discussion ouverte, appel possible à distance) ; appel : sonne 30 s (décrocher / refuser), sinon « Appel manqué » dans 🔔 avec « 📞 Rappeler » (permis à distance), décroché → voix WebRTC (micro coupable, écoute seule sans micro), raccrocher. 🔔 liste aussi les réponses à mes demandes, les discussions (non-lus) et les amis (en jeu / absent, 💬, 📞, retirer).
- **PNJ** : Tonton Koffi (flâne, missions), Aya, M. Fofana (épicerie), Tantie Adjoua (garba), M. Diabaté (emploi), clients du kiosque ; la liste serveur `NPCS` contient aussi ibrahim, seydou, fatou, awa, kouassi, bamba. « ! » jaune = mission à prendre / récompense à réclamer.

Détails : [docs/world-design.md](docs/world-design.md).

## 7. Simulation et économie (valeurs dans `rules.py` / `shared/city.json`)

- **Besoins** : faim +1,2/min, énergie −0,8/min de jeu actif ; départ faim 30, énergie 70 ; suspendus hors ligne (au-delà de 120 s entre deux requêtes). Travail refusé si énergie < 20 ou faim > 85. Énergie < 15 → marche −30 % (client).
- **Sieste** (zone `maison`) : +45 énergie, +4 faim, recharge 90 s.
- **Profils** : Étudiant 4 000 F · Salarié 8 000 · Artisan 5 000 (salaire ×1,25) · Indépendant 6 000 (×1,1) · Entrepreneur 9 000 (kiosque −20 %, débloqué d'office).
- **Commerces** : Épicerie (pain 150, eau 50, café Touba 200, sardines 450, casier 12 boissons 1 800) ; Garba d'Adjoua (garba 500, alloco 300). Stock quotidien par joueur.
- **Livraisons** : 3 colis parmi 4 destinations, 1 200 F × profil, ≥ 1,5 s entre livraisons, ≥ 30 s par service, expiration 15 min, 8 services/jour, coût −15 énergie +8 faim.
- **Kiosque** : 12 000 F (déblocage : 1 service terminé), vente 250 F, stock max 48, ≥ 4 s entre ventes, passif 2 boissons/h plafonné à 72 h d'absence (+1/h pendant une location de panneau).
- **Parcelles** : 15 000 F, 1 par joueur. Maisonnette 10 000 F, Petite boutique 18 000 F (enseigne 2–20 car.). Emplacement du bâtiment **calculé par le serveur** (`plots.placement`).
- **Panneau pub** : 2 000 F / 72 h, il faut une entreprise.
- **Missions** : Bonjour le quartier (300) → Courses (300) → Manger (200) ; Sieste (200) ; Premier boulot (500) → Épargne 12 000 F (800) ; Mon propre business (1 000) → Première vente (500) → 10 ventes (1 500) ; Propriétaire (1 000) → Bâtisseur (2 000).
- **Garanties** : atomicité (savepoint par action), sérialisation (verrou de ligne), idempotence, autorité serveur.

Détails : [docs/economy.md](docs/economy.md), [docs/game-design.md](docs/game-design.md).
